# 상품 데이터 설계 결정

테이블 스키마 기준은 `src/lib/catalog/schema.sql`, 수집 검색어 목록은 `src/lib/catalog/collectQueries.ts`다. 여기엔 왜 그렇게 만들었는지만 둔다.

## 데이터 소스: 구글 쇼핑 수집 DB

네이버 쇼핑 검색 API(`shop.json`)가 2026-07-31에 종료되어 2026-08-01부터 `404 SE05`를 반환한다. 네이버 개발자센터 약관 부칙 제2조 ③항으로 Search API 중 쇼핑, 책, 학술정보만 조기 종료됐고 NAVER API HUB로도 이관되지 않았다. 그래서 실시간 검색을 버리고 매일 수집해 DB에서 검색한다.

검토 후 기각한 대안:

| 대안                          | 기각 이유                                                     |
| ----------------------------- | ------------------------------------------------------------- |
| NAVER API HUB                 | 쇼핑 검색 미제공, 쇼핑인사이트는 트렌드 통계만                |
| 무신사 직접 수집              | robots.txt가 허용 명단 밖 봇을 `Disallow: /`로 차단           |
| 네이버 쇼핑 스크래핑 대행     | 봇 차단 우회 방식이라 약관 위반                               |
| 11번가 오픈API                | 무신사 상품 없음, 오픈마켓 셀러 상품이라 품질이 낮음          |
| 쿠팡 파트너스 API             | 무신사 상품 없음, 판매 실적 승인 조건                         |
| SerpApi 구글 쇼핑 실시간 호출 | 캐시 미적중 시 20~57초, 긴 검색어 0건, 판매처 목록 1곳만 반환 |

2026-09-15 실측: `google_shopping`(gl=kr)은 검색어에 "무신사"를 붙이면 40개 전부 무신사 상품이고 긴 검색어는 0건이 잦다. `google_immersive_product`는 0.4~1.9초에 판매처 직링크와 정리된 브랜드를 주지만 한국 결과는 판매처가 1곳뿐이다. 무신사 robots.txt는 `Storebot-Google`을 허용하므로 구글 쇼핑 노출 데이터는 무신사가 허용한 경로다.

## 인프라

- **Neon Postgres Free (싱가포르)**: 0.5GB로 여유 있고 유휴 시 잠들어도 1초 안에 깬다. Supabase는 7일 무요청 시 일시정지 후 수동 복구가 필요해 방문이 드문 포트폴리오에 위험하다. 서울 리전이 없어 싱가포르를 쓰며 왕복 지연은 AI 답변 시간 대비 체감되지 않는다
- **Vercel Cron (Hobby)**: 하루 1회 제한과 ±59분 오차는 일 단위 수집에 충분하다. GitHub Actions는 60일 무커밋 시 예약 실행이 꺼져 제외했다
- **SerpApi Free (월 250회, 카드 미등록)**: 초기 수집, 매일 수집 2회, 구매 링크 첫 클릭 조회에 나눠 쓴다. 매일 수집을 4회에서 2회로 줄여(한 달 약 60회) 클릭 조회 몫을 늘렸다. 카드가 없어 한도를 넘으면 요청만 거절되고, 수집과 상품 페이지 찾기만 멈추며 검색과 구매 링크(판매처 검색 대체)는 계속 동작한다. 평가자 하루 20~30클릭이면 한 달 중 일부 기간은 판매처 검색으로 간다

## 수집

- 검색어는 대부분 "무신사 + α" 형태다. α는 품목, 성별 + 품목, 브랜드, 스타일. 브랜드와 스타일 검색어는 프로필 선호 브랜드와 스타일에 맞는 상품이 DB에 충분히 있어야 추천에 반영되기 때문에 둔다. 여기에 `includeOtherMalls` 결과가 끊기지 않도록 "29CM 반팔티", "나이키 운동화" 같은 지원 판매처 검색어를 더한다
- 긴 검색어는 0건이 잦다. 2026-09-17 확인 결과 "무신사 + 스타일 + 품목" 27개 중 23개가 0건이라 결과가 나온 4개만 남기고 나머지는 "무신사 + 스타일" 2단어로 바꿨다
- `collect_queries.last_run_at`이 가장 오래된 것부터 순환한다. 목록에서 빠진 옛 검색어 행은 조회 대상에서 제외된다
- 이미 있는 상품은 가격, 이미지, 판매처 조회 토큰, `last_seen_at`만 갱신하고 **새 상품만** Gemini로 태깅한다. 태깅은 검색어 결과 단위로 한 번에 보낸다
- 태그: 한글 브랜드명, 브랜드를 뺀 상품명, 카테고리, 세부 품목, 성별, 색상, 소재, 스타일(`STYLE_OPTIONS` 안에서만), 검색 키워드, 패션 여부. 구글 상품명은 브랜드가 한영으로 붙어 있고 브랜드 필드가 없어 규칙 파싱보다 AI 정리가 정확했다
- 저장 기준(`shouldStore`): 패션 상품이고 중고, 도매 같은 노이즈 단어가 없으며 **지원 판매처**(`malls.ts`의 `SUPPORTED_MALLS`)인 상품. 지원 판매처가 아닌 결과는 태깅 전에 빼서 Gemini 호출도 줄인다
- 지원 판매처는 사이트 검색 주소로 검색 결과가 나오는지 확인한 곳만 둔다. 구매 링크가 상품 페이지를 모를 때 그 판매처 검색으로 보내야 해서 검색 주소를 모르는 판매처는 저장하지 않는다. 후루츠패밀리는 중고 거래 플랫폼이라 뺐고 솔드아웃, Vans, 드로우핏, 이랜드몰은 검색 주소를 확인하지 못해 뺐다. 예전에 AI가 신뢰 판매처를 판단하던 방식은 검색 주소가 없는 소규모 몰 140여 곳이 섞여 버렸다
- 판매처 표기는 `normalizeMall`로 대표 이름에 묶는다. 무신사 필터가 "MUSINSA", "무신사" 표기 차이로 새지 않게 하기 위함. 대표 이름은 화면에 보이지 않아 기존 DB 값(`thenorthface`, `Stand oil`)을 그대로 쓴다
- 지원 판매처 밖의 옛 상품은 검색과 비슷한 상품에서 빠지고 더 이상 발견되지 않아 60일 뒤 삭제된다
- 60일간 다시 발견되지 않은 상품은 삭제한다. 품절이나 판매 종료 상품이 오래 남지 않게 하기 위함
- 초기 수집은 로컬 `npm run db:seed`로 돌린다. 무료 플랜 시간당 50회 제한 때문에 검색어 사이 간격을 75초로 둔다

## 검색 (`searchProducts`)

1. **프로필과 찜 서버 반영**: AI가 생략한 스타일과 예산은 프로필로 채운다(`resolveSearchInput`). 이번 요청에 예산이 하나라도 있으면 프로필 예산과 섞지 않는다. 프로필 선호 브랜드와 찜 요약은 가산점용 취향으로 합친다(`buildPreferences`). 이유는 `agent.md`의 프로필 인자 측정
   - 찜은 프로필보다 한 단계 약하게 쓴다. 찜 브랜드는 프로필 브랜드와 같은 가산점, 찜 스타일은 요청과 프로필 스타일이 없을 때만 우선 채울 스타일(`pickStyles`)이 되고 평소엔 가산점, 찜 가격대는 예산이 없을 때만 가산점이다. 필터로 쓰지 않는 이유는 찜 몇 개로 결과를 좁히면 요청 맥락을 해치기 때문
2. **성별 필터**: 검색어의 "남자", "여자" 같은 단어는 키워드에서 빼고 태그 성별 필터로 바꾸며, 검색어에 없으면 프로필 성별을 쓴다. 공용 상품은 양쪽에 포함하되 정확히 같은 성별에 가산점을 준다. 키워드로만 두면 "여자 원피스"에 남성으로 태깅된 상품이 섞였다
3. **후보 조회**: 기본은 무신사 상품만, `includeOtherMalls`면 지원 판매처 전체에서 찾는다. 동의어와 띄어쓴 단어까지 펼친 키워드가 `search_text`에 하나라도 걸리는 상품을 요청 브랜드, 다른 판매처 요청 시 무신사 외 상품, 예산 안, 매칭 수, 선호 브랜드, 랜덤 순으로 300개 가져온다. 예산을 정렬에 넣은 이유는 매칭 상품이 많을 때 예산 안 상품이 개수 제한에 잘려 나가지 않게 하기 위함. `search_text`에 태그 키워드가 들어 있어 상품명에 없는 "여름", "청바지" 같은 표현도 걸린다
4. **예산 소프트 필터**: 예산 안 결과가 반환 개수보다 적으면 예산 밖도 포함하고 근접도 점수로 예산 안을 우선한다. 하드 필터는 결과가 통째로 비었다
5. **키워드 매칭**: 키워드와 무관한 후보를 빼되 전부 빠지면 후보를 유지한다
6. **동의어 보정**: 표기 차이(청바지↔데님)를 `KEYWORD_SYNONYMS`로 맞춘다. 짧아서 오매칭이 잦은 가방, 모자, 신발 일반어는 넣지 않는다
7. **재랭킹**: 키워드, 세부 품목, 요청 브랜드, 스타일, 선호 브랜드, 찜 스타일, 찜 가격대, 예산 근접도, 다른 판매처 요청 시 무신사 외 상품 점수. 세부 품목 가산점은 "니트" 검색에 "니트 넥타이"가 섞이던 문제 때문에 넣었다
8. **스타일**: AI 스타일 태그가 겹치면 일치로 보고, 태그가 없으면 상품명의 특징 단어(`STYLE_KEYWORDS`, 스트릿→와이드, 오버핏)로 판단한다
9. **가중 랜덤**: 상위 30개 풀에서 상위일수록 뽑힐 확률이 높게 반환한다. 균등 셔플은 정확도가 떨어지고 고정 상위는 매번 같은 결과라 "매번 다르되 좋은 게 더 자주"로 균형을 맞췄다. 풀이 18개일 때는 프로필이 있으면 같은 검색 10번에 서로 다른 상품이 16개뿐이었다
10. **본 상품 제외**: 같은 대화와 이전 방문에서 이미 보여준 상품(`shownIds`)은 풀 뒤로 보내 새 상품이 모자랄 때만 쓴다. 기록은 브라우저 localStorage에 최근 300개(`src/utils/seenProducts.ts`)이고 대화를 지워도 남는다. 대화를 지우고 같은 질문을 해도 다른 상품이 나와야 상품이 많다고 느끼기 때문
11. **선택 순서**(`pickProducts`): 선호 스타일이나 선호 브랜드(프로필과 찜)에 맞는 새 상품, 이미 본 선호 상품 최대 2개, 나머지 새 상품, 나머지 본 상품 순이다. 브랜드당 최대 2개로 제한하고 모자라면 한도를 넘겨 채운다. 선호 상품이 적은 품목에서 본 상품을 완전히 빼면 두세 번째 검색부터 선호 스타일이 사라져서 선호 상품 일부만 다시 보여주는 쪽으로 균형을 맞췄다. 브랜드를 스타일과 같은 우선순위로 둔 이유는 스타일을 먼저 채우던 때 선호 브랜드 비율이 0%였기 때문
12. **다른 판매처 자리**(`pickWithOtherMalls`): `includeOtherMalls`면 6자리 중 최대 3자리를 무신사 외 상품에 먼저 배정하고 점수에 밀린 무신사 외 상품도 풀에 남긴다. 스타일 태그가 맞는 무신사 상품이 앞자리를 채워 "다른 데서도"에 무신사만 나오던 문제 때문
13. **예산 밖 표시**: 예산 안 상품이 모자라 예산 밖이 섞이면 출력에 `outOfBudget: true`를 싣는다. AI가 예산 밖 카드를 보여주면서 "결과가 없다"고 답하던 문제 때문
14. **반복 안내**: 같은 대화에서 이미 보여준 상품이 3개 이상 다시 나오면 출력에 `notice`를 싣는다. AI가 프롬프트 규칙보다 Tool 결과 문구를 잘 따라서 안내를 결과에 넣었다. 이전 방문에서 본 상품은 세지 않는다. 새 대화 첫 질문부터 "대부분 보여드렸어요"라고 답하던 문제 때문
15. **작은 풀 채우기**: 새 상품과 다른 후보가 모자라면 이미 본 선호 상품으로 6칸을 끝까지 채운다. 선호 상품 재등장 한도 때문에 5개만 나오던 문제 때문
16. **색상 요청**(`extractColorIntent`): "비비드, 컬러풀, 밝은"은 원색 가산점과 블랙 계열 감점, "어두운, 무채색"은 반대, "파스텔, 연한"은 연한 색 가산점으로 바꾼다. "컬러, 색상" 같은 일반어는 상품명 매칭에서 뺀다("컬러풀한 바지"에 "아디컬러 저지"가 걸리던 문제). 품목과 색상 이름이 함께 오면 색상 이름("베이지", "빨간")은 검색어에서 빼고 가산점 색상으로 옮겨 후보를 품목으로만 찾는다. 색상 요청이 있으면 선택 순서의 선호 기준을 스타일 대신 색상으로 바꾼다
17. **후속 요청의 품목 유지**(`withPreviousItemKeywords`): 검색어가 색상뿐이면 같은 대화의 직전 검색 키워드(`collectLastSearchKeywords`)에서 품목을 붙인다. "반바지 → 다른컬러도"에서 AI가 품목을 빠뜨려 백팩, 후드집업이 나오던 문제 때문

색상 한계: 색상 태그는 수집 때 상품명에 드러난 색상만 붙어서 대부분 비어 있다(5만원대 반바지 11개 중 비비드 표기 1개, 어두운 색 3개, 정보 없음 7개). 이미지로 색상을 태깅해야 색상 검색이 제대로 동작하지만 규모가 커서 보류했다.

측정(2026-09-15, 상품 약 1,800개, 요청당 6개 × 8회): AI가 인자를 빠뜨린 경우 예산 안 44% → 100%, 스타일 일치 60% → 100%, "여자 원피스" 성별 일치 98% → 100%. 찜만 있고 프로필이 없을 때(찜: 빈티지, 4~7만원, 요청당 6개 × 10회) 빈티지 비율은 반팔티 12% → 95%, 셔츠 7% → 67%, 찜 가격대 비율은 셔츠 30% → 93%. 선호 브랜드와 스타일 비율은 해당 품목의 상품 수에 좌우된다(무신사 맨투맨 45개 중 빈티지 2개). 그래서 브랜드와 스타일 검색어 수집으로 보강한다.

측정(2026-09-17, 상품 약 3,400개, 프로필: 빈티지, 커버낫, 남성, 3~8만원, 반팔티 요청 × 8회 연속 본 상품 제외): 예산 안과 성별 일치 100%, 빈티지 비율 15% → 27%, 커버낫 비율 6% → 17%, 이전 상품 재등장 48개 중 12개. 조건에 맞는 빈티지 반팔티가 7개, 커버낫 반팔티가 3개뿐이라 스타일과 브랜드 비율에는 데이터 상한이 있다. 프로필이 없으면 대화를 지우고 같은 질문을 5번 해도 겹침 0개다.

## 가격비교를 없앤 이유

같은 상품을 판매처별로 모아 최저가를 보여주는 모달과 `comparePrices` Tool이 있었지만 제거했다. 구글 쇼핑은 검색어당 40개만 주고 한국 결과에 판매처 묶음이 없어, 같은 상품이 무신사와 다른 몰에서 함께 수집되는 경우가 거의 없었다. 무신사 상품 150개를 샘플로 돌리면 150개 전부 판매처가 1곳이었다. 브랜드 검색어로 여러 몰을 모아도 서로 다른 상품만 모였다.

## 구매 링크 (`/go/[id]`)

- 미리보기의 구매 링크는 `/go/{id}`. 서버가 아래 순서로 이동할 곳을 정해 302 이동한다(`resolveProductUrl`)
  1. 저장된 `direct_url`이 상품 판매처 도메인이면 그 상품 페이지
  2. 수집한 지 24시간 안이면 판매처 조회 토큰으로 SerpApi를 호출해 같은 판매처 도메인 링크를 저장하고 이동
  3. SerpApi 구글 웹검색(`site:판매처 도메인 브랜드 상품명`)으로 상품 상세 페이지를 찾아 저장하고 이동. 긴 검색어로 못 찾으면 짧은 검색어(앞 5단어)로 한 번 더 찾고 제한 시간은 15초
  4. 그 외에는 그 판매처 사이트의 검색 결과(`buildMallSearchUrl`). 지원 판매처 밖의 옛 상품은 무신사 검색
- 토큰 조건을 둔 이유: 2026-09-17 실측에서 이틀 전 토큰은 판매처 목록이 빈 값으로 오고 당일 토큰은 1.8초에 링크를 줬다. 구글 쇼핑 상품 페이지(`product_link`)도 같이 만료돼 "찾을 수 없음"이 떴다. 만료된 토큰 조회는 크레딧만 쓰므로 호출하지 않는다
- 판매처 도메인 검사를 둔 이유: 판매처 목록의 첫 링크를 저장하던 때 무신사 상품에 다른 쇼핑몰 링크가 저장됐다
- 검색어(`buildSearchKeyword`)는 브랜드와 상품명에서 괄호 표기, 색상 수 표기, 기호 단어를 빼고 앞 6단어만 쓴다. 긴 검색어는 판매처 검색에서 0건이 되기 쉽다
- 구글 웹검색을 쓰는 이유: 웹검색 결과는 판매처의 실제 상품 주소라 토큰처럼 만료되지 않는다. 2026-09-17 무신사 7개, KREAM, Nike, 29CM 각 1개로 시험하니 10개 중 9개가 정확한 상품 페이지를 찾았다(29CM는 결과 없음)
- 틀린 상품을 피하는 규칙(`pickSearchResultLink`, `scoreProductTitle`). 확신이 없으면 틀린 상품 대신 판매처 검색으로 보낸다
  - 판매처 도메인이고 상품 상세 경로(`productPath`, 무신사와 KREAM은 `/products/번호`)에 맞는 링크만 채택하고, 추천과 후기 같은 목록 페이지는 뺀다. 무신사 `goodsNo=번호` 주소는 상품 페이지로 바꾼다
  - 상품명 단어의 절반 이상이 제목이나 요약에 있어야 하고, 제목에서 맞은 단어는 2점, 요약에서만 맞은 단어는 1점으로 가장 높은 결과를 고른다. 단어 2개만 맞으면 첫 결과를 고르던 때 같은 브랜드의 다른 상품("Pride Prove")과 다른 색상("Nori-White")으로 갔다
  - 상품명에 영문 이름이나 모델명(Nori, PACER)이 있으면 결과에도 있어야 하고, 결과 제목에 상품에 없는 영문 이름이 있으면 버린다. 구글 제목이 "...티셔츠. ..."처럼 잘려 구분 이름이 안 보이는 경우 때문이고, 요약(snippet)에는 "Nori-Pink" 같은 전체 이름이 있어 점수에 넣었다
  - 구글은 긴 검색어에서 사이트 제한을 무시하고 유튜브 같은 엉뚱한 결과를 주기도 해서 짧은 검색어로 한 번 더 찾는다
- 판매처 조회는 상품마다 크레딧 1회라 수집 시점엔 토큰만 저장한다. 무신사 앱 링크(`link.musinsa.com/app/goods/{id}`)는 웹 상품 페이지로 바꾸고 `srsltid` 추적 파라미터를 뗀다
- 상품이 DB에 없으면 홈으로 보낸다
